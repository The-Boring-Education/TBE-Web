## S1: Seed and Browse One Synthetic Shiksha Course

> This was generated by AI during triage.

Source: [OSS data PRD](oss-development-data.md). Proposed category: enhancement.

### What to Build

Provide a documented, explicitly targeted local fixture command that previews,
seeds, and safely resets one synthetic Shiksha course and its chapters. A
contributor can start the existing API/platform apps and browse that fixture
without access to production data. Use established models and local test helpers;
coordinate setup documentation with existing contributor-guide PR #1241.

### Acceptance Criteria

- [ ] Validate an approved local host and exact dedicated OSS database before connecting; reject remote, SRV, production mode, or non-OSS targets.
- [ ] Dry run reports intended records and produces no database writes or external sends.
- [ ] Synthetic fixture identities are stable and a second run does not duplicate records.
- [ ] Reset affects fixture-owned records only and preserves an unrelated sentinel record in each collection.
- [ ] The course can be listed and its public chapter content browsed through the actual app/API path.
- [ ] Tests cover target refusal, repeat runs, reset isolation, and valid references.
- [ ] Documentation states local prerequisites and authentication limitations without adding an auth bypass.

### Blocked By

None after the local-target/reset specification and this brief are approved.

## S2: Add DSA Fixtures and Access/Progress Scenarios

- [ ] Progress fixtures verify completed/incomplete states without awarding real points or mutating a real account.
- [ ] Repeated seed/reset obey S1's identity and namespace rules.
- [ ] Tests and instructions identify which scenarios are local browsing versus mocked authenticated verification.

### Blocked By

publishing the approved queue in dependency order.

## S3: Preserve Shiksha Chapter URLs and Browser History

> This was generated by AI during triage.

Source: [Shiksha PRD](shiksha-learning-ux.md). Proposed category: enhancement;
OSS candidate. This is a behavior requirement, not a claimed production repro.

### What to Build

Make chapter navigation durable through the existing chapter query parameter.
The selected list row, content, and URL agree across direct links, refresh, Back,
and Forward. For an invalid chapter identifier, select the first available
chapter and normalize with history replacement; if none exist, show the existing
empty state. Navigation itself must not mutate progress or certificates.

### Acceptance Criteria

- [ ] Selecting chapter B updates the URL and refresh returns to B.
- [ ] Back and Forward restore the corresponding selected chapter and content.
- [ ] An invalid identifier normalizes once to the first available chapter without a router loop.
- [ ] Empty and non-enrolled cases retain their established access behavior.
- [ ] Router tests and one mocked-course browser test cover these cases.
- [ ] Chapter navigation creates no completion, enrollment, or certificate write.

### Blocked By

None after this brief is approved. Coordinate with other changes to the learn
page; use existing course mocks rather than waiting for S1.

## S4: Handle Progress-Save Failures and Chapter-Switch Races

> This was generated by AI during triage.

Source: [Shiksha PRD](shiksha-learning-ux.md). Proposed category: enhancement;
OSS candidate. No live failure has been reproduced during planning.

### What to Build

Make completion mutations resilient to failure and navigation. Capture the target
course/chapter when submitting, retain confirmed progress until success, show
pending/error/retry feedback, and update the captured chapter only. Do not change
the server's award or certificate policy.

### Acceptance Criteria

- [ ] A pending operation cannot be submitted repeatedly for the same chapter.
- [ ] Failed saves preserve confirmed completion and expose an accessible retry.
- [ ] Start saving A, navigate to B, and resolve A: only A's completion changes.
- [ ] A response for a previous course instance cannot mutate the newly opened course.
- [ ] A successful retry issues only the intended mutation and uses existing feedback contracts.
- [ ] Deferred-response tests cover success, failure, retry, and navigation races.
- [ ] No new certificate or award request is introduced by error handling or navigation.

### Blocked By

None after this brief is approved. S3 and S4 are behavior-independent but touch
the same page; coordinate branches or sequence their merges to reduce conflicts.

## S5: Make the Mobile Chapter Drawer Keyboard-Accessible

> This was generated by AI during triage.

Source: [Shiksha PRD](shiksha-learning-ux.md). Proposed category: enhancement;
OSS candidate, with beginner suitability to be reviewed.

### What to Build

Bring the mobile chapter drawer into the repository's existing accessible
dialog/drawer pattern. Preserve chapter selection and desktop layout. Do not
combine this with a full-page redesign or a new modal dependency.

### Acceptance Criteria

- [ ] The trigger and drawer have accessible names and accurate expanded/open state.
- [ ] Opening moves focus to an appropriate element; Escape closes the drawer.
- [ ] Modal focus stays in the drawer and background controls are not interactive while it is open.
- [ ] Dismissal restores focus to the trigger; chapter selection closes the drawer and focuses meaningful content.
- [ ] Long chapter names and narrow viewports do not hide selection or close controls.
- [ ] Keyboard-focused browser tests cover open, navigation, selection, dismissal, and focus return.
- [ ] Desktop navigation and completion behavior remain unchanged.

### Blocked By

None after this brief is approved. Coordinate with S3/S4 because the same learning
page is involved, even though the behavior does not depend on those changes.
