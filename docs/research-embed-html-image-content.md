# Research: Embedding HTML/Images into Learning Content

## Problem Statement

When we generate content via LLMs for a topic and want to embed it into our learning content, we need to understand:

1. How to **showcase** HTML and images within learning content
2. How to **store** that content (including inline HTML and image assets)
3. How to **update** it efficiently over time

---

## 1. Current Content Systems in TBE-Web

### 1.1 MDXRenderer (Markdown-based learning content)

**Location:** `packages/components/src/common/MDXRenderer/index.tsx`

- Uses **markdown-it** with `html: true`, which already supports inline HTML tags.
- Content is stored as a **Markdown string** (`mdxSource`) in the database and rendered client-side via `dangerouslySetInnerHTML`.
- Custom renderers exist for headings, bold, lists, links, code blocks, and YouTube embeds (links auto-converted to `<iframe>`).
- An `<aside>` HTML block handler already demonstrates inline HTML support.
- Supports LaTeX math rendering through a custom plugin.

**Key takeaway:** Inline HTML is already parsed and rendered. Images and HTML blocks generated by an LLM can be embedded directly inside the Markdown string.

### 1.2 Resources App (Full HTML content)

**Location:** `apps/resources/`

- Content lives as **standalone HTML files** under `apps/resources/content/<slug>/index.html` with a companion `meta.json`.
- The `ResourceArticle` component renders full HTML via `dangerouslySetInnerHTML`.
- Style tags are extracted and injected separately for scoped styling.

**Key takeaway:** This system already supports arbitrary HTML and images—ideal for rich, design-heavy content generated by LLMs.

### 1.3 StudyGuide Model (Structured JSON content)

**Location:** `apps/api/src/lib/database/models/InterviewPrep/StudyGuide.ts`

- Content is stored as **structured JSON** in MongoDB (`Schema.Types.Mixed` for section content).
- Sections have typed structures: `intro`, `concept`, `pattern`, `cheatsheet`—each with typed sub-fields like `bodyText`, `codeBlocks`, `tableData`.
- No explicit image or HTML field exists in the current schema.

**Key takeaway:** To support images/HTML here, the schema needs extension (see proposals below).

## 2. How to Showcase HTML in Learning Content

### Option A: Inline HTML in Markdown (MDXRenderer path)

LLM-generated content can include inline HTML directly within the Markdown string:

```markdown
## Understanding Arrays

Arrays store elements in contiguous memory.

<div class="illustration">
  <img src="https://cdn.example.com/array-diagram.png" alt="Array memory layout" />
</div>

Here is an interactive example:

<div class="interactive-embed" data-type="code-playground">
  <pre><code>const arr = [1, 2, 3];</code></pre>
</div>
```

**Pros:**
- Already supported by `markdown-it` with `html: true`.
- No schema changes needed—content is a single string field.
- LLMs naturally produce Markdown with HTML.

**Cons:**
- XSS risk from `dangerouslySetInnerHTML`—requires sanitization.
- Complex interactive widgets need custom rendering logic.

### Option B: Structured Content Blocks (StudyGuide path)

Add explicit block types to the structured JSON schema:

```
section.content.blocks = [
  { type: "text", body: "Arrays store elements..." },
  { type: "image", src: "https://cdn.../diagram.png", alt: "...", caption: "..." },
  { type: "html", html: "<div class='interactive'>...</div>" },
  { type: "code", language: "javascript", code: "const x = 1;" }
]
```

**Pros:**
- Fine-grained control over each block's rendering and styling.
- Easier to validate, version, and selectively update blocks.
- Can enforce image optimization (srcset, lazy loading) at the component level.

**Cons:**
- Requires schema migration and new renderer components.
- More complex for LLMs to produce (need strict JSON output format).

### Option C: Hybrid (Recommended)

Use Markdown with inline HTML as the **authoring format** (what the LLM produces), but parse it into structured blocks for **storage and rendering**. This combines natural LLM output with structured control.

## 3. How to Store Content with Images

### 3.1 Image Storage Options

| Approach | Description | Pros | Cons |
|---|---|---|---|
| **External CDN URLs** | Store image URLs pointing to a CDN (e.g., Cloudflare R2, AWS S3 + CloudFront, Cloudinary) | Fast delivery, no DB bloat, easy cache invalidation | Requires separate upload pipeline, URL management |
| **Base64 inline** | Embed images as `data:image/png;base64,...` in the content string | No external dependencies, single document | Massively inflates document size, no caching, slow rendering |
| **Asset references** | Store asset IDs in content, resolve to CDN URLs at render time | Decoupled, supports image versioning | Extra lookup step, more complex |

**Recommendation:** Use **External CDN URLs** (e.g., Cloudinary or S3+CloudFront). Store the full URL in the content field. This is how most content platforms (Notion, Medium, Hashnode) handle it.

### 3.2 Proposed Image Upload Flow

```
LLM generates content with image placeholders
        ↓
Backend receives content + image files/URLs
        ↓
Images uploaded to CDN (S3/Cloudinary/R2)
        ↓
CDN URLs replace placeholders in content
        ↓
Final content string saved to MongoDB
```

### 3.3 Database Storage

**For MDXRenderer content (Markdown string):**
- No schema change needed. Images are simply `![alt](cdn-url)` or `<img src="cdn-url" />` in the Markdown.
- Store the entire Markdown string as-is in the existing field.

**For StudyGuide structured content (JSON):**
- Add an `images` array or support an `image` block type in sections:

```
// Option 1: Add images array to section content
{
  type: "concept",
  content: {
    pageTitle: "...",
    subtitle: "...",
    subsections: [...],
    images: [
      { id: "img-1", src: "https://cdn.../img.png", alt: "...", caption: "..." }
    ]
  }
}

// Option 2: Mixed content blocks (more flexible)
{
  type: "concept",
  content: {
    pageTitle: "...",
    blocks: [
      { type: "text", body: "..." },
      { type: "image", src: "https://cdn.../img.png", alt: "...", width: 600 },
      { type: "html", html: "<div>...</div>" },
      { type: "code", language: "python", code: "..." }
    ]
  }
}
```

## 4. How to Update Content

### 4.1 Full Replacement

- LLM regenerates the entire topic content.
- Replace the stored Markdown string or JSON document.
- Simple but loses manual edits/customizations.

### 4.2 Section-level Updates (Recommended for StudyGuide)

- Each section has an `id` field (already exists in StudyGuide schema).
- To update: regenerate specific sections, match by `id`, and replace.
- Preserves unchanged sections and allows targeted regeneration.

```
PATCH /api/v1/study-guide/:topicId/sections/:sectionId
Body: { content: { ... updated section content ... } }
```

### 4.3 Block-level Updates (For structured block content)

- Each block within a section gets a unique `blockId`.
- Update individual blocks (e.g., replace one image, update one paragraph).
- Most granular control, best for incremental LLM updates.

### 4.4 Version History

- Store a `version` field and optionally keep previous versions.
- Enables rollback if LLM-generated updates introduce errors.
- Can be implemented with a `contentVersions` subcollection or a separate `ContentHistory` model.

## 5. Rendering Images Safely

### 5.1 Sanitization

Since `dangerouslySetInnerHTML` is used in both MDXRenderer and ResourceArticle, HTML content must be sanitized before rendering:

- Use a library like **DOMPurify** to strip malicious tags/attributes while preserving safe HTML (`<img>`, `<div>`, `<table>`, etc.).
- Allow-list specific tags and attributes relevant to learning content.

### 5.2 Image Optimization

For images in learning content, apply these optimizations at the component level:

- **Lazy loading:** Add `loading="lazy"` to `<img>` tags.
- **Responsive sizing:** Use `srcset` and `sizes` attributes, or a CDN transform URL (e.g., Cloudinary auto-format).
- **Alt text:** Ensure all images have descriptive `alt` attributes (important for accessibility and SEO).
- **WebP/AVIF:** Use CDN auto-format to serve modern formats.

### 5.3 Adding Image Support to MDXRenderer

Add a custom `image` rule to the existing MDXRenderer:

```
md.renderer.rules.image = (tokens, idx) => {
  const token = tokens[idx];
  const src = token.attrGet("src");
  const alt = token.content || "";
  return `<img src="${src}" alt="${alt}" loading="lazy" class="rounded my-4 max-w-full" />`;
};
```

This ensures all Markdown images (`![alt](url)`) are rendered with consistent styling and lazy loading.

## 6. Summary of Recommendations

| Concern | Recommendation |
|---|---|
| **Authoring format** | Markdown with inline HTML (natural LLM output) |
| **Image storage** | External CDN (Cloudinary/S3+CloudFront) with URLs in content |
| **Content storage** | Markdown string for MDXRenderer; extend StudyGuide schema with block types for structured content |
| **Rendering** | Enhance MDXRenderer with custom image rules; sanitize HTML with DOMPurify |
| **Updating** | Section-level replacement by ID for StudyGuide; full string replacement for Markdown content |
| **Versioning** | Add `version` field and optional history collection for rollback |
| **Security** | Sanitize all HTML before `dangerouslySetInnerHTML`; allow-list safe tags |
| **Performance** | Lazy loading, CDN auto-format (WebP/AVIF), responsive image sizes |
